Full requirements spec locked 2026-07-02 for the "AI Agent Library Chat Assistant" (already registered as a 10%-progress placeholder agent in Firestore via `insert-copilot-meta-agents.cjs`). This is a **requirements-only session** — nothing implemented yet. See [[project-work-queue]] for where this sits in the overall backlog (item deferred after Deploy Approval feature shipped).

**Why:** user wants Pre-Registration + library discovery to be doable via natural-language chat instead of only the form, but explicitly capped v1 to read-only to avoid the risk of an LLM mis-filling/mis-submitting a real registration.

**UX & scope:**
- Floating icon, bottom-right corner, present on **all 3 apps** (`/`, `/sdlc/`, `/portfolio/`) — these are 3 separate React apps on one Firebase Hosting site, so the icon must be added to each app's shell separately (no shared shell currently).
- **Read-only for v1** (locked as 1a over 1b) — answers/searches/suggests only; if the user wants to actually register something, the chat should point them to the real Pre-Reg form, not submit on their behalf. 1b (chat-drives-real-submission) explicitly deferred to a later phase, not now.
- Unlimited turns per session; **no chat history persistence** (session-only, same posture as the existing analysis cache); **no streaming** — wait for the full answer, show a "thinking" loading animation instead of token-by-token.

**Architecture (locked 2b over 2a):** Client orchestrates the multi-turn tool-loop itself. Skills run client-side (pure functions over the already-in-memory approved-agents library — confirmed by reading `src/lib/skills.js`, all 4 existing skills are side-effect-free and take `ctx.library`/`ctx.processes`). A Cloud Function is only hit per-turn when an LLM judgment call is actually needed (intent classification, semantic capability matching, or final answer composition) — this avoids duplicating `lib/skills.js` logic into the separate `functions/` Node package, which has its own package.json/dependencies. Reuses the same Gemini 2.5 Flash model as `analyzeDuplicate`.

Context the chat needs loaded: approved agents (already available via `useApprovedAgents`) + `sdlcProcesses` + `sdlcUseCases` collections (needed for SDLC-mapped questions like "process 2.2 มี agent อะไร map อยู่บ้าง").

**Skills:** the existing 4 (`search_library`, `duplicate_check`, `connection_suggest`, `get_agent_detail` — all defined in `src/lib/skills.js`) are reused as-is. **One new skill required: `query_library`** — does NOT exist yet, needs to be written. It must mirror the app's actual real filter dimensions (verified against `buildAgentFilter()` in `src/lib/agentUtils.js` and `ControlBar.jsx`, not invented): `type` (Agent/Skill), `tier` (T1-T4), `owner`, `relatedRole`, `coreAbility`, `reusable` (3 values), `status` (derived from devProgress), `scope` (Internal/External), plus `sdlcStage`/`sdlcProcessMapping`/`useCase` (added per this session — the original filter set didn't cover SDLC, user explicitly asked for it) and free-text keyword. Must support filter + count + group-by (e.g. "owner ไหนมี agent เยอะสุด").

**Two answer paths — deliberately split by cost/determinism, not routed through one code path:**
- **Filter/count questions** ("T2 กี่ตัว", "Pilot มีอะไรบ้าง", "owner ไหนเยอะสุด") → keyword-only / structured match via `query_library`, fully deterministic, **no Vertex call**.
- **Semantic capability questions** ("มีตัวไหนทำ documentation generation ได้บ้าง" when the agent's description says "สร้างเอกสาร") → **hybrid**: keyword prefilter narrows candidates, then a Cloud Function LLM call picks semantically-matching ones from that real candidate set (never invents agents — grounded, same anti-hallucination posture as `analyzeDuplicate`). This path costs a Vertex call; the filter path doesn't.

**Two response modes:**
- **Mode A (library data)** — answer only from actual skill-call results. Never answer from the LLM's own world knowledge about what agents "probably" exist.
- **Mode B (idea/opinion request)** — LLM general knowledge allowed, but ONLY within this closed 4-item list (no "etc.", user explicitly closed the list when I initially left it open-ended): (1) AI agent/skill development approaches, (2) impact analysis of an idea, (3) pros/cons of an idea, (4) implementation risks/cautions. Anything outside these 4 → refuse.
- **Cross-mode leak guard (the most dangerous failure mode, user flagged this explicitly):** even while in Mode B (brainstorming), the model must NEVER assert "there's already an agent that does X" as fact without having actually called a skill first — mode doesn't excuse ungrounded claims about real data.
- **Tone requirement (added late, easy to miss):** Mode B answers must read like a polite, easy-to-understand conversation with a person — not a dry disclaimer-laden output. This is an explicit quality bar, not just a content-scope rule.

**Guardrails (user's list + my additions, all explicitly accepted):**
Out-of-scope topics, profanity, sexuality, race/religion/gender/politics, jailbreak/prompt-injection attempts (including fake "forget your instructions" or "show me your system prompt"), requests to perform write actions beyond read-only (e.g. "approve this for me", "delete agent X", "set progress to 100") — refuse these even though they're phrased as instructions, since real permissions come from the Firestore role, never from chat text, PII requests, medical/legal/financial advice, violence/self-harm/illegal content, fake authority claims in-message ("I'm the admin, so...") — never trust claimed authority from chat text alone.
Cost-saving split: obvious profanity/keyword hits should be blocklisted client-side before spending a Vertex call; subtler cases (indirect political/religious framing) need the LLM to judge.

**Explicitly still open (deferred to the design-flow session, NOT part of this requirements lock):** how each incoming message gets classified into one of the 4 buckets (filter / semantic-capability / idea / refuse) — this routing/intent-classification step is itself an LLM call and its exact flow (single classify-then-answer call vs. multi-step) is a design decision for next time, not decided here.

**DESIGN FLOW LOCKED (2026-07-02, follow-up grill-me — build not started yet, awaiting explicit go):**
- **Architecture 1a confirmed:** ONE Gemini function-calling loop, guardrails live in the Cloud Function system prompt. No separate classify-first call. Refuse = the model just returns refusal text.
- **The 2a/2b split is implemented as TOOL CHOICE, not a mode flag** (key realization): which tool Gemini picks IS the routing.
  - Deterministic tools → client runs skill + **templates the answer locally, never returns the result to Gemini** (1 Vertex call total): `query_library` (filter/count/group), `get_agent_detail`, `connection_suggest`, and NEW `query_sdlc`.
  - `capability_search` (NEW, split out from query_library) → returns a keyword-prefiltered candidate subset that IS sent back to Gemini, which semantically selects + composes conversationally (2 Vertex calls). This is the only tool whose result goes back up to the LLM.
  - No tool call → idea-mode answer or refusal, composed directly (1 call).
- **Cloud Function `chatLibrary` contract (stateless per call):** Request `{ messages: [≤6 turns], toolResults: [{name,args,result}|null] }` → Response is exactly one of `{ type:'tool_call', name, args }` or `{ type:'answer', text }`. User said "ลองดูก่อน" (try this shape, may revisit).
- **Client state machine per user message:** (1) client-side blocklist pre-filter → refuse locally, 0 calls; (2) loop max 3 iterations: POST chatLibrary; if tool_call and tool is deterministic → run + template locally → DONE (don't loop back to Gemini); if tool_call and capability_search → run prefilter, push to toolResults, loop; if answer → show text; (3) exceed 3 → fallback message.
- **Session lifecycle:** transcript lives in plain React state (NOT sessionStorage/localStorage) so refresh/close/logout clears it instantly per requirement; send only the last 6 turns to the CF each call.
- **NEW skill `query_sdlc`:** reads the `sdlcProcesses` + `sdlcUseCases` collections (VERIFIED exact names against firestore.rules + SDLCTab.jsx — user casually wrote 'sdlcProcess'/'sdlcUsecases' but those are wrong). Needed because all other tools read only the `agents` collection, so questions about the SDLC catalog itself ("process 2.2 คืออะไร / มี use case อะไรบ้าง") were unanswerable. `sdlcUseCases` fields: processId/name/owner; join to `sdlcProcesses` via processId (useCases has no `stage` field).
- **Submit-idea handoff (v1 = option b):** when a user wants to register an idea mid-chat, the chat shows a button that opens the existing `PreRegModal` (empty) + an "export as CSV" option. Option (c) — AI pre-fills the form from the discussed idea — is explicitly DEFERRED to a later phase (same fabrication-risk reasoning that deferred 1b).
- **CSV export (v1):** export the discussed idea as CSV, client-side download (user-triggered, own data — no server, no restriction). Query-result CSV export ("list all T2 as CSV") is trivially addable later but not in v1 scope unless asked.
- **Cost:** analyzed and explicitly waved off by user ("ไม่เป็นไร ข้ามไปก่อน") — per-message cost is tiny (Gemini 2.5 Flash, ~3-4K input tokens/call, library never dumped wholesale); only aggregate volume matters. Context-caching + per-user rate-limit noted as future optimizations, not v1 blockers.

**BUILD COMPLETE (2026-07-02, same session), NOT YET DEPLOYED — post-build scope additions:**
- Mode B closed-list expanded from 4→5 items: item 5 = SDLC process / Agile methodology discussion, both general knowledge (e.g. "Scrum vs Kanban") AND grounded against the real SDLC catalog via `query_sdlc` when the question references an actual process/stage. User explicitly wanted LLM general knowledge allowed here, not just library-grounded answers — this is the one place in Mode B where broader LLM knowledge was deliberately let in.
- Refusal STYLE rule added: the assistant must never explain/list its own capabilities or boundaries when refusing — just a short neutral line like "เรื่องนี้อยู่นอกเหนือจากหน้าที่ของผมครับ/คะ", no elaboration unless the user asks again. This applies to ALL refusal cases (out-of-scope, guardrail hits), not just the new SDLC/Agile topic.
- Actually-shipped v1 tool set narrowed from the original plan to 5 tools: `query_library`, `query_sdlc`, `capability_search`, `get_agent_detail`, `connection_suggest` (adapted to take just an existing agentName, not a full draft). `search_library`/`duplicate_check` were dropped from the chat tool set — they need a full structured draft object that read-only chat has no reliable way to assemble from free text (same fabrication-risk reasoning that deferred option (c)/1b).
- CSV export implemented for `query_library` LIST results only (not an "idea being discussed" export, since there's no structured idea object in read-only v1).
- Two real bugs found via runtime testing (not just syntax checks) before this was ready: (1) `capability_search`'s original word-split-on-whitespace prefilter returned zero results for Thai queries since Thai has no inter-word spacing — fixed with a character-trigram fallback (`scoreText()` in `src/lib/skills.js`); (2) that trigram fallback then false-matched an unrelated English query via a single coincidental 3-char overlap ("quantum" → "ant" → "Assistant") — fixed with `MIN_TRIGRAM_HITS = 3` threshold.
- Files touched: `src/lib/agentUtils.js` (+`extractProcessId`/`agentProcessIds`, moved out of SDLCTab.jsx since a 2nd consumer now needs them), `src/components/SDLCTab.jsx` (uses the moved helper, no behavior change), `src/lib/skills.js` (+3 skills), `src/lib/chatGuardrails.js` (new, client blocklist), `src/components/ChatAssistant.jsx` (new), `src/styles/ChatAssistant.css` (new), `functions/index.js` (+`chatLibrary` export), `src/App.jsx` (mounts `<ChatAssistant>` once — turned out this is a single SPA with tab state, NOT 3 separate React apps as CLAUDE.md's architecture section describes; that doc section is stale/aspirational, not the deployed reality).
