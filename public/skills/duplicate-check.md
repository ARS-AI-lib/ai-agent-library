# Skill: Agent/Skill Duplicate Check

> ตรวจว่าไอเดีย AI agent/skill ที่กำลังจะสร้าง "ซ้ำ" กับของที่มีอยู่แล้วใน catalog หรือไม่
> พร้อมคะแนนความมั่นใจและระดับความเสี่ยง — ใช้ได้กับ AI assistant ทุกตัว (Claude, ChatGPT, Gemini ฯลฯ)

---

## เงื่อนไขการใช้งาน (Requirements)

1. **ต้องมีข้อมูล catalog แนบมาด้วยเสมอ** — ไฟล์ CSV/ตารางของ agent/skill ที่มีอยู่ อย่างน้อยต้องมีคอลัมน์:
   `agentName, description, coreAbility, input, output, businessValue`
   (ขาดคอลัมน์ไหน ให้ข้ามการให้คะแนน field นั้นแล้วเกลี่ยน้ำหนักที่เหลือตามสัดส่วนเดิม)
2. **ต้องมี "draft"** — ข้อมูลไอเดียใหม่ที่จะตรวจ ในโครงเดียวกับข้อ 1
3. skill นี้เป็น read-only: วิเคราะห์และรายงานเท่านั้น ห้ามสรุปว่า "อนุมัติ/ไม่อนุมัติ" แทนมนุษย์

## วิธีเรียกใช้

วางไฟล์นี้ + ไฟล์ catalog ให้ AI แล้วสั่ง:

```
ใช้ skill duplicate-check ตรวจ draft นี้กับ catalog ที่แนบ:
ชื่อ: <agentName>
คำอธิบาย: <description>
ความสามารถหลัก: <coreAbility>
Input: <input>
Output: <output>
Business Value: <businessValue>
```

---

## ขั้นตอน (Instructions สำหรับ AI)

### 1) Normalize ข้อความก่อนเทียบทุกครั้ง
- แปลงเป็นตัวพิมพ์เล็กทั้งหมด
- ตัดคำว่า "tbc" ทิ้ง (ถือเป็นข้อมูลยังไม่ระบุ)
- แทนที่เครื่องหมาย `. , ; : ( ) / - _` ด้วยช่องว่าง แล้วยุบช่องว่างซ้ำ
- field ที่เป็น list (เช่น coreAbility หลายค่า) ให้ join ด้วย ", " ก่อน

### 2) คะแนนความคล้ายต่อ field (0–100)
ใช้ค่าที่**มากกว่า**ระหว่างสองวิธีนี้:
- **Token overlap (Jaccard):** แตกเป็นคำ (เอาเฉพาะคำยาว > 2 ตัวอักษร) → `(จำนวนคำร่วม ÷ จำนวนคำรวมแบบไม่ซ้ำ) × 100`
- **String similarity (Levenshtein):** `(1 − edit_distance ÷ ความยาวสตริงที่ยาวกว่า) × 100`
- ถ้า normalize แล้วเหมือนกันเป๊ะ = 100 / ถ้าฝั่งใดฝั่งหนึ่งว่าง = 0

⚠️ **ภาษาไทยไม่มีวรรคระหว่างคำ** — token overlap จะพลาดง่าย ถ้าเทียบข้อความไทยให้คุณ (AI) ใช้วิจารณญาณเชิงความหมายประกอบ แล้วระบุในรายงานว่าคะแนนส่วนไหนมาจาก rule ส่วนไหนมาจากการตีความ

### 3) รวมคะแนนแบบถ่วงน้ำหนัก
| Field | น้ำหนัก |
|---|---|
| agentName | 0.25 |
| description | 0.25 |
| coreAbility | 0.15 |
| input | 0.15 |
| output | 0.15 |
| businessValue | 0.05 |

`confidence = Σ (คะแนน field × น้ำหนัก)` — ปัดทศนิยม 1 ตำแหน่ง

### 4) ระดับความเสี่ยง
| Confidence | ระดับ | ความหมาย |
|---|---|---|
| ≥ 80 | 🔴 Critical | แทบแน่นอนว่าซ้ำ — ควรใช้/ต่อยอดของเดิมแทน |
| 60–79 | 🟠 High | ทับซ้อนสูง — ต้องอธิบายให้ได้ว่าต่างจากของเดิมตรงไหน |
| 40–59 | 🟡 Medium | ทับซ้อนบางส่วน — พิจารณา integrate กับของเดิม |
| < 40 | 🟢 Low | ไม่ถือว่าซ้ำ (ไม่ต้องรายงานรายตัว) |

### 5) กติกาการตัดสินเพิ่มเติม (สำคัญ — ได้จากบทเรียนใช้งานจริง)
- **Sub-function overlap สำคัญกว่า text similarity** — draft ที่รวมงานของหลายตัวเดิม ("kitchen-sink") อาจได้คะแนน rule ต่ำทั้งที่ซ้ำจริง ถ้าพบว่า draft ทับซ้อนกับของเดิม **ตั้งแต่ 3 รายการขึ้นไป** ให้ยกธง "ทับซ้อนหลายตัว" แม้แต่ละตัวจะคะแนนไม่สูง
- ดู **สถานะ reusable ของของเดิม** ประกอบ: ของเดิมที่ "Reusable" = สัญญาณแรงว่าควรใช้ซ้ำแทนการสร้างใหม่; "Non-reusable" = อาจมีเหตุให้สร้างใหม่ได้
- ถ้า catalog มีรายการที่ถูก **archive** แล้ว: ใช้เตือนว่า "เคยมีคนทำแล้วเลิกเพราะ..." ได้ แต่**ห้ามเสนอเป็นตัวให้ไป reuse**

### 6) รูปแบบรายงานผล
รายงานเฉพาะรายการที่ confidence ≥ 40 (สูงสุด 5 อันดับ เรียงมากไปน้อย):
```
## ผลตรวจความซ้ำซ้อน: <ชื่อ draft>
ความเสี่ยงโดยรวม: <ระดับสูงสุดที่พบ>

1. <ชื่อของเดิม> — <confidence>% (<ระดับ>)
   ตรงกันมากที่สุด: <field ที่คะแนนสูงสุด 2 อันดับ>
   ข้อสังเกต: <วิเคราะห์สั้นๆ ว่าซ้ำเชิงเนื้อหาจริงไหม หรือแค่คำพ้อง>
...
สรุปคำแนะนำ: <สร้างใหม่ได้ / ควรใช้ของเดิม / ควรคุยกับ owner ของ X ก่อน>
```
